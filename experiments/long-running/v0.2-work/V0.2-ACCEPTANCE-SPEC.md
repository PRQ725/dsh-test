# V0.2 ACCEPTANCE SPEC (frozen before candidate verification)

Status: **FROZEN (revision of the v0.2 baseline for v0.2-rc.1)** - this file is the acceptance
baseline for the Long-running Toolkit v0.2 line. It was written and pinned **before** the
candidate was verified, so a verification result cannot redefine what "pass" means. It was
re-opened once, under explicit human authorization, for the v0.2-rc.1 release-readiness revision;
that revision is recorded as amendment A3 and it changes one check, not the bar.

Frozen at: 2026-10-09 (v0.2 baseline round); revised 2026-10-09 for v0.2-rc.1
Scope: the v0.2 development candidate and its rc.1 revision only. It does **not** touch,
supersede or re-judge the first pilot, its frozen six-file artifact, or `Evaluator v0`.

---

## 0. Why a new evaluator, and why not the old one

`experiments/long-running/check.ps1` is `Evaluator v0` for the six-file v0.1 artifact: its
required heading/field sets encode the v0.1 structure. The v0.2 candidate is an eight-file
structure whose section names differ by design, so `check.ps1` is **not** an admissible
judge for it. Reusing it would either force v0.1 wording into v0.2 or produce a meaningless
FAIL; both are dishonest.

| Object | Judge | Status |
|---|---|---|
| v0.1 pilot artifact (six files, frozen) | `experiments/long-running/check.ps1` (Evaluator v0, SHA256 `F3D22F99...`) | unchanged, out of scope this round |
| v0.2 candidate (eight files) | `experiments/long-running/v0.2-work/evaluator/check-v0.2.ps1` | new, frozen by this spec |

`Evaluator v0` is not modified, not re-run against v0.2, and not deleted. The v0.2 candidate
is **allowed** to fail `check.ps1`; that is expected and is not a defect.

This is a deliberate ceiling: the toolkit is a policy layer plus blank forms, not a
documentation set.

### Evaluator interface (frozen)

```
check-v0.2.ps1 -Root <toolkit-root> [-Proposal <candidate-root>] [-Workspace <repo-root>]
               [-Mode Candidate|Hygiene|Adoption|Readiness] [-InstanceRoot <directory>]
               -GoalContract <GOAL.md path> [-InstanceRootDeclared <directory>]
```

Four modes, four different guarantees. **`-GoalContract` is required by `-Mode Adoption` and
`-Mode Readiness`** and is refused (exit 2) when missing; it is not used by `-Mode Candidate` or
`-Mode Hygiene`. See amendment A5.

| Mode | What it judges | What a green result may claim |
|---|---|---|
| `Candidate` | the portable eight-file toolkit itself | `CANDIDATE VALIDATION PASS` |
| `Hygiene` | the adopting project's instance **directory** only | `HYGIENE PASS` plus `CONTRACT NOT CHECKED` |
| `Adoption` | hygiene **and** the frozen contract's instance-root declaration | `ADOPTION PASS (contract-verified)` |
| `Readiness` | hygiene, contract verification, and the twelve-item initialization contract | `INITIALIZATION READINESS` per-item, with human gates `PENDING` |

`-InstanceRoot` applies to `-Mode Hygiene`, `-Mode Adoption` and `-Mode Readiness`. It names the
directory the caller wants inspected. When it is omitted, the documented default
`<projectRoot>/docs/long-running/` is used. The evaluator always prints the path it inspected,
marked `(declared)` or `(default)`, so a PASS can never be claimed against a path nobody can see.

`-GoalContract` names the project's frozen objective contract. The evaluator reads its
`Instance root:` field and requires the inspected directory to be the **same directory**, compared
after normalization (absolute form, `\`/`/` equivalence, Windows case-insensitivity, trailing
separators ignored, a relative value resolved against the project root). A mismatch, an unfilled
declaration, a missing field, or an unreadable contract is fail-closed.

`-InstanceRootDeclared` supplies the declared instance root directly, for the case where the
contract file cannot be reached. It is an input, not a check: supplying it does not prove the
contract says so, and the evaluator says which of the two it used. It does **not** substitute for
`-GoalContract` in `-Mode Adoption` or `-Mode Readiness`.

Exit codes (fixed):

| Code | Meaning |
|---|---|
| 0 | PASS / READY - no failure reasons |
| 1 | FAIL - one or more concrete printed reasons |
| 2 | ERROR - bad invocation (including `-Mode Adoption`/`-Mode Readiness` without `-GoalContract`), unreadable root, unusable scratch, or internal failure |
| 3 | NOT READY (`-Mode Readiness` only) - a checkable prerequisite is **missing** (`FAIL`), instance hygiene failed, or a **human gate is PENDING** and therefore unclosed |

Exit code 3 exists so that "hygienically fine, not yet ready" cannot be reported as success by a
caller that only looks at the exit code. `-Mode Readiness` returns 0 **only** when every checkable
prerequisite passed and no human gate is open; that is still not acceptance, and it arms nothing.
The evaluator must be **read-only** and must never read a model-declared completion claim.

## 4. What this evaluator deliberately cannot decide

A mechanical PASS proves: the eight files exist, meet their minimum size, carry the required
sections and fields, are internally consistent and portable, distinguish contract from
implementation, and label HARD/SOFT honestly. It proves **nothing** about whether the
guidance is good, adoptable, or correctly generalised from DSH `0.2.0-rc.2`.

The following are reserved to a human and are never inferred from a green evaluator:

- `HUMAN CONTENT ACCEPTANCE` of the v0.2 candidate.
- Whether the adoption dry-run's outcome is meaningful.
- Whether the version-bound claims are correct.
- `PUBLICATION` of the candidate into `toolkit/long-running/v0.2/`.

A mechanically clean document set can still be worthless. The evaluator is a necessary
condition, never a sufficient one.

## 5. Verification sequence (frozen order)

1. This spec is written and frozen.
2. The candidate is written (eight files).
3. `evaluator/check-v0.2.ps1` is written, then its SHA256 is recorded in
   `evidence/CHECK-REPORT.md` **before** the first scored run.
4. `evaluator/check-v0.2.selftest.ps1` runs and must print `SELFTEST PASS` (exit 0).
5. `check-v0.2.ps1 -Mode Candidate` runs against the candidate; raw stdout and exit code are
   recorded verbatim. Any FAIL is fixed **in the candidate**, never by editing this spec or
   the evaluator's checks.
6. The bounded adoption dry-run is performed per `README.md`.
7. `check-v0.2.ps1 -Mode Adoption` runs against the dry-run project; raw stdout and exit code
   are recorded.
8. `CHANGE-LIST.md` records the change inventory and the evidence paths.
9. All of the above is reported; then the round **stops for human review**.

## 7. Amendments

Amendments are dated, reasoned, and append-only. An amendment may not lower a check; it may
correct a check that was specified against the wrong object. Each amendment is visible in the
evaluator source as an in-line comment at the check it changes. A1 and A2 were made while the
candidate was still unverified; A3 was made under explicit human authorization for the
v0.2-rc.1 release-readiness revision. None of them has been removed or rewritten.

**A1 (2026-10-09) - V12 in `-Mode Adoption` inspected the wrong object.** As first written, the
rule scanned the toolkit root for the `UNFILLED` marker. The first real adoption run showed this
could never pass in a correct adoption: a copied toolkit keeps its blank forms on purpose, and
an adopter who fills them in place has destroyed the reusable template. V12 now locates the
adopting project root (nearest `.git` or `.dsh` ancestor, bounded to five levels), scans the
project's own filled instances under `docs/long-running/`, and fails if any of them still
carries the marker or if none exists. No other check changed.

**A2 (2026-10-09) - the reference pattern must not use a backtick lookbehind.** The pattern for
`templates/<name>.md` was written with a backtick-assertion lookaround. On this host the
pattern never matched, because a backtick inside a double-quoted PowerShell string is an escape
character rather than a literal. The pattern is now the plain
`templates/[A-Za-z0-9._\-]+\.md`, whose character class already excludes the backtick
delimiter. This removed five false failures without weakening any check; the harness's T2 case
still proves a broken reference is caught.

**A3 (2026-10-09, v0.2-rc.1) - the instance location is now declared, not hard-coded.**

*What was wrong.* A1 fixed V12 to scan the project's filled instances, but fixed their location
to `<projectRoot>/docs/long-running/`. The candidate `README.md` Step 3 tells the adopter to
create "a small working area inside the target project" and does not prescribe that path. A live
probe confirmed the consequence: an adopter who keeps the filled `GOAL.md` / `PLAN.md` /
`STATE.md` in `planning/` - entirely legitimate under the toolkit's own README - was failed with
`V12 no filled project documents found …`. The check was measuring a convention that the toolkit
never stated.

*What replaces it.* The toolkit now declares the convention, and the evaluator consumes the
declaration instead of assuming it:

1. `README.md` Step 3 states the **default layout** (`toolkit/long-running/` for the reusable
   copy, `docs/long-running/` for the project's filled instances) and states that a project may
   choose another directory **only if it declares it explicitly**.
2. `templates/GOAL.md` gains one field, `Instance root:`, which records that declaration in the
   project's own frozen objective contract. It is the declaration of record; the AI reads it
   rather than guessing.
3. `SKILL.md` requires the agent to read the declared instance root and pass it explicitly.
4. `templates/FINAL-REPORT.md` gains the same `Instance root:` field, because the report is
   written into that directory and must not be the only artifact whose location is implicit.
5. `check-v0.2.ps1` gains `-InstanceRoot <directory>` for `-Mode Adoption`. When omitted, the
   **documented default** is used, and the evaluator prints which path it inspected, marked
   `(declared)` or `(default)`.
6. In adoption mode the instance root must exist, must hold at least one `.md` instance, and
   must hold no `UNFILLED` marker. A missing, empty, or unfilled instance root is a FAIL whose
   reason names the path. A missing project root (no `.git` and no `.dsh` marker) is a FAIL.
7. The toolkit's own reusable `templates/` directory is never an admissible instance root, and
   is rejected by name if a caller passes it.

*What this does not do.* It does not force every project onto `docs/long-running/`; it makes the
default explicit and the alternative declarable. It does not make the evaluator read the
`Instance root:` field: the field is the project's declaration, and the command-line parameter is
the adopter's explicit instruction to the judge. Keeping those two mechanisms separate means a
toolkit file can never silently redirect the judge.

*Effect on the previous default.* Unchanged: a project that puts its instances in
`docs/long-running/` and passes no `-InstanceRoot` behaves exactly as before, except that the
path is now printed. No other check is affected; V1-V11 and R1-R3 are byte-for-byte the same
rules.

**A4 (2026-10-09, v0.2-rc.2) - three contract repairs found by an independent content review.**

*What was wrong.*

1. **F1.** The round-execution guidance was written as an absolute: one round equals one
   increment, and "a round that tries to finish everything verifies nothing". The first pilot's
   own evidence contradicts it as a rule - its round 1 produced all six deliverables, ran the
   evaluator, recorded a FAIL, fixed it, re-ran to PASS, wrote its evidence and satisfied its
   acceptance gate, after which four rounds had no content work left. The sentence punished the
   behaviour that actually worked and could be read as an instruction to pad rounds.
2. **F2.** The rc.1 rule "if the `Instance root:` field and the directory on disk disagree, the
   directory wins" let the current filesystem layout, or a model's reading of it, override a
   frozen human-approved declaration. It also allowed `-InstanceRoot` to name a different
   directory than the project declared and still produce a PASS.
3. **F3.** V12's checks were described as if they established that a project was ready to start a
   goal. They establish only that the instance root exists, holds at least one `.md`, holds no
   `UNFILLED`, and is not the toolkit's own templates.

*What changes.*

- **V14 (new)** fixes F1 as a *documentation* rule, not a new mechanism: a round may complete a
  bounded set of related increments and may complete the whole objective; what matters is that
  the work maps to the objective, is verified in the same round, leaves trustworthy evidence,
  satisfies the frozen success criteria, and leaves no substantive work outstanding. Splitting
  work to consume budget is forbidden, mechanical PASS is not acceptance, and no wording may
  claim that `READY FOR HUMAN REVIEW` stops the driver.
- **V13 (new)** fixes F2. The evaluator gains `-GoalContract` (path to the project's frozen
  objective contract) and `-InstanceRootDeclared` (the declared root, supplied directly when the
  contract cannot be reached). When a declared root is available the inspected root must be the
  **same directory** after normalization: absolute form, `/` and `\` treated alike, Windows
  case-insensitive comparison, trailing separators ignored, and a relative declared value
  resolved against the project root before comparison. A mismatch, an unfilled `Instance root:`
  field, or an unreadable declaration is **fail-closed**: no Adoption PASS, no Readiness READY.
  The evaluator never substitutes another existing directory, and it never edits the contract.
  When no declaration is available it may use the documented default, and it must say so.
- **V15 (new) and the readiness mode** fix F3. INSTANCE HYGIENE (V12) and INITIALIZATION
  READINESS are now separate names with separate verdicts. A new `-Mode Readiness` reports the
  twelve-item contract item by item as `PASS` (mechanically checkable and satisfied),
  `POLICY` (a policy record is present and structurally valid - which is not authorization),
  `PENDING` (a human gate with no recorded authorization), or `FAIL` (a checkable prerequisite is
  absent). Exit code **3** means "hygienically fine, not ready", so a caller that only reads exit
  codes cannot mistake one for the other. The twelve items: filled `GOAL.md`; `PLAN.md` present
  with an approval record; initialized `STATE.md`; filled `EVALUATION.md`; a project evaluator
  present; evaluator test evidence present; a frozen evaluator hash recorded; budget and stop
  conditions stated; workspace and permission boundary verified; instance-root consistency;
  human approval records; and a determined final-report path and owner.
- `templates/PLAN.md` gains an additive `Approval record:` field, because a readiness item that
  asks whether a plan was approved needs a place where that answer is written rather than
  inferred from prose.
- `templates/EVALUATION.md` gains an additive `Initialization readiness:` block stating the
  contract and marking which items are human gates.

*What does not change.* A1-A3 stand. V1-V11, R1-R3 and the `-Mode Candidate` field sets are
untouched except for the two additive fields named above. No check is relaxed: V12 keeps every
rc.1 requirement and only has its scope renamed. Exit codes 0/1/2 keep their meaning; 3 is added.

*Effect on previous results.* The rc.1 results remain valid for what they measured: a rc.1
Adoption PASS still means instance hygiene passed under the rc.1 rules. It does **not** become a
statement about initialization readiness, because the rc.1 run never made one. Any rc.1 PASS
that involved a declared custom instance root should be re-read under V13; the rc.1 records
themselves are unchanged and must not be rewritten.

*What stays a human judgement.* Whether a plan was **genuinely** approved, whether the workspace
boundary was **deliberately** accepted, whether the evaluator's tests were **adequate**, and
whether the guidance is good. The evaluator reports `POLICY` or `PENDING` for these and never
claims to have verified them by finding a word in a file.

**A5 (2026-10-09, v0.2-rc.3) - the guarantee scope of each verdict is now explicit.**

*What was wrong.* A4 made `-GoalContract` **optional**. When a caller omitted it, the evaluator
printed `instance-root consistency: UNCHECKED` on the same screen as a green instance-hygiene
verdict. That is not a false statement about the directory, but it is a false *impression* about
the run: a reader - human or model - could take the green verdict as a complete adoption
certification, when the one check that ties the inspected directory to the project's frozen,
human-approved declaration had silently not happened. The defect is in the **scope of the
claim**, not in the check.

*The guarantee each result carries.*

| Result | Proves | Does **not** prove |
|---|---|---|
| **Candidate Validation** (`-Mode Candidate`) | the portable eight-file toolkit satisfies V1-V15 and R1-R3 | anything about a target project; it does not read that project's contract |
| **Instance Hygiene** (`-Mode Hygiene`) | the instance directory is reachable, holds instance documents, holds no blank-form marker, is not the toolkit's own `templates/`, and satisfies the basic directory constraints | that the instance root matches the frozen goal, that initialization is complete, that human approval exists, or that a goal may be created or armed |
| **Contract-verified Adoption** (`-Mode Adoption`) | everything Instance Hygiene proves, **plus** that the frozen contract was readable, its `Instance root:` declaration existed and was valid, and the inspected path equalled the declared path after normalization | initialization readiness; human approval; that a goal may be armed |
| **Initialization Readiness** (`-Mode Readiness`) | hygiene and contract verification, plus a per-item verdict on the twelve-item readiness contract | acceptance; it arms nothing, and its human gates stay `PENDING` until a person closes them |

*Full Adoption necessary conditions.* `-Mode Adoption` does not issue an `ADOPTION PASS` unless
**all** of the following hold: `-GoalContract` was supplied (or `-InstanceRootDeclared`, with the
output naming which); the contract was readable; the `Instance root:` field was present and not
unfilled; the normalized declared path equalled the normalized inspected path; and instance
hygiene passed. If `-GoalContract` is absent the invocation is refused with `ERROR` (exit 2) -
the run does not silently downgrade to a weaker verdict.

*Hygiene-only output restriction.* `-Mode Hygiene` exists so that a directory-only check remains
available without weakening the word "adoption". It may run with no declaration, and then it must
print `HYGIENE PASS` together with `CONTRACT NOT CHECKED`; it must never print `ADOPTION PASS`,
never claim contract consistency, and never be presented as readiness or as authorization to arm
a goal.

*Readiness and the contract.* `-Mode Readiness` also requires `-GoalContract` and refuses without
it (exit 2). `UNCHECKED` consistency is never treated as satisfied, and item R10 reports `PENDING`
rather than any kind of pass when consistency could not be established. Readiness is unchanged in
every other respect: it does not create or arm a goal, and it never converts text into human
approval.

*Interface and compatibility.* One mode is added (`Hygiene`); `-GoalContract` becomes required for
two existing modes; check V16 is added to police the vocabulary; exit code 2 now covers the
missing-contract invocation. `-Mode Candidate` is untouched. `-Mode Adoption` is **stronger** than
it was at rc.2: an invocation that used to succeed with `UNCHECKED` consistency now fails closed,
which is the intended correction and is recorded here rather than presented as a no-op.

*Effect on earlier results.* The rc.1 and rc.2 adoption results remain valid **for what they
measured**: each was an instance-hygiene result, and those that also supplied a declaration were
contract-consistent as well. They are not retroactively relabelled, and no rc.1 or rc.2 log is
rewritten. Read under A5, an rc.1/rc.2 green run whose output said `UNCHECKED` was a hygiene
result, not a complete adoption certification - which is precisely the ambiguity A5 removes.

*New regression requirements.* R3-T1 to R3-T12 in section 6: candidate validation without a
contract; adoption refused without one; adoption passing with one; unreadable contract; unfilled
declaration; conflict; equivalent spellings; hygiene-only vocabulary; readiness without a
contract; readiness with open human gates; the existing discrimination cases retained; and the
candidate files unchanged by any of it.
