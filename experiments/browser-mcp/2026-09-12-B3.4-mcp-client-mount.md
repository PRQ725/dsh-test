**一个有意的偏离（已记录）**：我**省略了 `reconnect`**。

## INFERENCE

1. **`insert` 不带 `id` 的语义再次得到实证**：新增条目出现在根列表**末尾**（L541），
   且层注释归属正确。这与 `applyEntryPatches` L83 `else data.push(...insert)` 的实现一致。

2. **`reconnect` 省略是安全的**：dump 中该条目**没有**被补出 `reconnect` 字段
   （dump 反映 patch 的 JSON 安全形态，不做 schema 默认值填充），
   而运行时由 `resolveReconnectPolicy` 兜底。因此"dump 里看不到 reconnect"是正常的，
   **不代表配置缺失**。

3. **`patchReload: live` 意味着该条目理论上可热加载**，但本阶段**未 boot**，
   因此**无法从运行时观察**热重载行为（也不在本阶段范围）。

4. **隔离性是结构性的、已被实证**：patch 层按 profile 目录解析，
   browser-lab 的改动对 web 的合成树**零影响**（dump 逐字节相同）。

5. **本阶段达成了"前三项"中的后两项**：② Entry configured、③ Entry present in composed tree。
   第 ④ 项（runtime actually started）**尚未、也不能在本阶段证明** ——
   因为 `command: npx` 的 spawn 只发生在 **boot** 时，而本阶段禁止 boot。

6. **下一阶段存在一个已知风险**：`failOnStartupError: true` 会让**首次 npx 下载/启动失败**
   直接导致 profile 启动失败（而不是"静默少工具"）。这是有意的可诊断性选择，
   但在首次联网解析 `@playwright/mcp@latest` 时可能表现为启动报错 —— 需在 boot 阶段预期并观察。

7. **web 实例被手动重启这一事实提示**：实验期间环境仍在被人为操作，
   因此后续 boot 阶段的"端口占用"判断需要**先重新确认 3080 的持有者**，不能沿用旧 PID。
